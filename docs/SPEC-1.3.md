## 1. 現況與已知事實

以下是本規格的設計前提。「來源」欄標明是實測、讀設定、計算或推論。

| 事實 | 來源 | 影響 |
|------|------|------|
| `dpd_delay = 20s`、`dpd_action = restart`、`mobike = no` | 讀 `swanctl.conf` | charon 只會對**同一台**閘道重試；沒有 MOBIKE，本機 IP 改變時通道不會跟著遷移 |
| 重送參數 `charon.retransmit_*` 為預設值（逾時 4 秒、重試 5 次、倍數 1.8）。一次 DPD 送出後約 165 秒才判定失聯，加上 `dpd_delay` 約 **185 秒** | 讀 `charon.conf`；依官方文件的公式計算，未實測 | 只靠目前的 DPD 發現斷線太慢（F1、F2）。第一次連線不受影響：輔助程式的 `up` 已用 `swanctl --initiate --timeout 20` 限制，連不上的閘道約 20～25 秒放棄 |
| charon 的 log **沒有寫入檔案，也沒有進系統日誌**：`charon-logging.conf` 的 `filelog`、`syslog` 區塊是空的。目前只能用輔助程式的 `log` 子命令即時看，**沒有歷史紀錄** | 讀設定檔；先前 `diag.sh` 收集 log 的段落為空 | F3：要先補 log 設定 |
| strongSwan 的 `filelog` 沒有檔案大小上限或輪替功能 | strongSwan 文件（`filelog` 只有 `path`、`append`、`default`、`flush_line`、`time_format` 等選項） | F3：log 大小要另外控制 |
| 三台閘道中只有一台回應 ICMP ping，三台的 TCP 443／10443 都不通 | `ping -c 3`、`nc -z` 實測 | F4：**連線前無法可靠地量出每台閘道的延遲** |
| `swanctl --list-sas` 的 `local '<IKE 身分>' @ <本機 IP>[<埠>]`：引號內是 IKE 身分，`@` 後面才是本機 IP（目前身分預設用 IP，兩個值剛好一樣） | 真實連線的輸出 | F1：本機 IP 要解析 `@` 後面的位址 |
| VPN 的虛擬 IP 掛在 `utun` 介面上（strongSwan 的 kernel-pfroute 建立），每次連線、斷線都會新增或移除這個介面 | 先前 `diag.sh` 的路由表（虛擬 IP 在 `utun6`） | F1：`NWPathMonitor` 會因為 App 自己的連線動作而觸發，必須過濾 |
| `list-sas` 有 `established <N>s ago`；[推論] IKE SA 金鑰更新（每 86400 秒）後會重新計算 | 真實連線的輸出；金鑰更新行為未實測 | F1：只在 App 啟動時用它初始化「已連線時間」 |
| `NWPathMonitor` 提供介面與可用狀態，但不提供 IP 位址 | Apple 文件 | F1：IP 要另外用 `getifaddrs` 取得 |
| 輔助程式只接受固定參數；`up auto` 在輔助程式裡寫死 vpn1→2→3 的順序，只回傳最後結果；App 每 3 秒呼叫一次 `status`，解析時只讀前三個欄位 | 1.2.0 原始碼 | F1、F3、F4 都要改輔助程式，見 §2 |

## 2. 共用改動

### 2.1 輔助程式升版

新功能需要的 root 操作集中在這一次升版。App 會比對內附版本，不同就在「環境檢查」顯示「需要更新」，使用者按一次就好。

| 子命令 | 變更 | 用途 |
|--------|------|------|
| `status` | 輸出多兩個欄位：`connected <連線> <虛擬IP> <本機IP> <已建立秒數>` | F1 |
| `up N` | 不變（只連指定那台） | F4：**App 自己逐台呼叫 `up 1`、`up 2`…**，才能記錄每台的結果與耗時。`up auto` 保留給命令列使用 |
| `reload-settings`（新增） | 以 root 執行 `swanctl --reload-settings`，讓 charon 重新讀取 `strongswan.conf` | F1（重送參數）、F3（log 設定） |
| `logtrim`（新增） | charon 的 log 超過 2 MB 時就地截斷，只保留最後 1 MB | F3 |

相容性：
- **舊 App 配新輔助程式**：1.2.0 的解析只讀前三個欄位，多出來的欄位會被忽略，不受影響。
- **新 App 配舊輔助程式**（還沒按「更新」）：`status` 只有三個欄位，也沒有 `reload-settings`、`logtrim`。App 要能辨識，這時停用「比對本機 IP」「用已建立秒數初始化」「log 截斷」，其餘照舊運作；「環境檢查」提示更新。
- **§2.2 的參數何時生效**：參數寫在設定檔，要 charon 重新載入才會生效。輔助程式更新完成後，App 立刻呼叫一次 `reload-settings`。在那之前，只有 charon 重新啟動時才會套用；而輔助程式只在 charon 沒在執行時才會啟動它，實際上等於要重開機，所以**不能依賴「下次啟動」**。

### 2.2 連線參數調整（寫進 App 產生的設定檔）

| 參數 | 目前 | 改為 | 理由 |
|------|------|------|------|
| `dpd_delay` | 20s | 10s | 更快發現失聯 |
| `dpd_action`（CHILD_SA 層級，寫在 `children.corp`） | restart | clear（strongSwan 的預設值，這裡明確寫出） | 重連統一由 App 處理，避免 charon 與 App 同時重試（見 Q1） |
| `charon.retransmit_timeout` | 4.0 | 2.0 | 寫在 `/opt/homebrew/etc/strongswan.d/splitswan.conf`，由 App 產生 |
| `charon.retransmit_tries` | 5 | 3 | 同上 |
| `charon.retransmit_base` | 1.8 | 1.5 | 同上 |

[計算] 調整後，一次 DPD 送出到判定失聯約 2＋3＋4.5＋6.75 ≈ 16 秒，加上 `dpd_delay` 約 **26 秒**（原本約 185 秒）。重送參數也會套用在第一次連線，所以連不上的閘道約 16 秒就會放棄（原本由 `--timeout 20` 限制在約 20～25 秒）。**數字要實測確認**（Q6）。

## 3. F1 自動重連

### 3.1 目標

使用者按過「連線」之後，除非自己按「斷線」，否則 App 要盡量讓通道維持連線，包括睡眠喚醒、切換網路、閘道暫時中斷這幾種情況。

### 3.2 連線意圖

- 新增狀態 `wantConnected`，存在 UserDefaults。
- 使用者按「連線」→ 設為 `true`。**只有使用者按「斷線」才會設為 `false`**。結束 App、登出、關機都不會改變它，所以重新登入後 App 自動啟動時會接回去。
- App 啟動時，如果 `wantConnected == true`：
  - 目前 `disconnected` → 自動連一次
  - 目前 `connecting`（例：命令列或上一個 App 程序留下的連線動作）→ **不要**再呼叫 `up`，套用「卡在連線中」的 30 秒規則
  - 目前 `connected` → 不動作

### 3.3 事件與處理

所有連線動作（使用者手動、自動重連）都經過同一個**連線協調器**，同一時間只執行一個動作。

| 事件 | 偵測方式 | 處理 |
|------|----------|------|
| 睡眠喚醒 | `NSWorkspace.didWakeNotification` | 等 5 秒讓網路就緒，**一律重建通道**（`down` 後重連）。原因：同一個 Wi-Fi 下，本機 IP 沒變、SA 看起來還在，但閘道那邊可能早就刪掉了；與其等 DPD 發現，不如直接重建，只多花幾秒 |
| 網路改變（換 Wi-Fi、插拔網路線、熱點） | `NWPathMonitor` 路徑變更，再用 `getifaddrs` 取主要介面的 IPv4。**主要介面排除 `utun*`、`ipsec*` 與虛擬 IP** | 等 3 秒穩定。IPv4 跟 SA 的本機 IP（`@` 後面）不同 → 重建通道；相同 → 不動作 |
| 通道失聯 | 每 3 秒的 `status` 從 `connected` 變成 `disconnected`（`dpd_action = clear` 之後，DPD 判定失聯時 SA 會被移除） | 重連 |
| 卡在連線中 | `status` 持續 `connecting` 超過 30 秒 | 視為一次失敗，`down` 後照退避流程重試 |

去重與互斥：
- 3 秒內的多個事件合併成一次處理。
- **喚醒後 15 秒內的網路變更，併入這次喚醒重建**，不另外處理（喚醒後網路常在 4～8 秒才就緒，3 秒的合併時間蓋不住）。
- **App 自己執行 `up`／`down` 期間與結束後 10 秒內**的路徑變更一律忽略，也不重設退避（避免 utun 介面的增減觸發重建迴圈）。
- 協調器執行中收到喚醒或網路事件：不中斷目前的動作，只標記「完成後重新檢查」；動作完成後比對一次 IP，不同才重建。
- 協調器執行中（不論是使用者操作或自動重連），輪詢看到的狀態變化只更新畫面，**不觸發**新的重連。App 自己做 `down` 造成的斷線，也不算失聯。
- **「斷線」可以搶先**：`up` 正在執行時（最多約 20 秒，無法中斷）按「斷線」，立刻設 `wantConnected = false`、取消後續重試，畫面顯示「斷線中」；等目前的 `up` 回來後，不論成功與否都馬上執行 `down`。這樣不會出現「已連線但使用者想斷線」的狀態。

### 3.4 重連與退避

- 照 F4 的順序逐台嘗試，每台逾時約 16 秒（§2.2）。
- 一整輪都失敗後，依序等 5、15、30、60 秒再試，之後固定每 60 秒一次，不會停止。
- **網路改變或喚醒時重設退避**（從 5 秒重新開始），因為換了網路，先前的失敗已經沒有參考價值。
- 沒有網路時（`NWPathMonitor` 狀態為 `unsatisfied`）暫停重試，網路恢復後立刻試一次。

### 3.5 已連線時間

- App 啟動時如果已經連著，用 `已建立秒數` 初始化 `connectedSince`；之後由 App 自己持續計時，不再跟著 SA 的秒數走，避免 IKE 金鑰更新後歸零。
- 自動重建通道（喚醒、換網路）不歸零。只有真的失聯、而且沒在 30 秒內恢復，才重新計時。

### 3.6 驗收條件

- [ ] 連線後闔上筆電 5 分鐘再打開，**上次成功的閘道可以連上時**，喚醒後 30 秒內恢復連線，不需要手動操作
- [ ] 連線中把 Wi-Fi 換成手機熱點，30 秒內在新網路上重新連線（同樣假設該閘道可以連上）
- [ ] 手動按「斷線」後，睡眠喚醒、換網路、重新啟動 App 都**不會**自動連線
- [ ] 連線中登出再登入（或重開機），App 自動啟動後會自動連線
- [ ] 連線中用 `pfctl` 擋掉往閘道的 UDP 500、4500 **與 ESP（IP 協定 50）**（沒有 NAT 時 ESP 不走 UDP，只擋 UDP 不會觸發 DPD）→ 約 30 秒內偵測到失聯並開始重連；持續擋住時照 5→15→30→60 秒的間隔重試，不會每 3 秒猛打
- [ ] 解除封鎖後，下一次重試就連上
- [ ] 拔掉網路線（沒有網路）時暫停重試；插回去後 10 秒內開始重連
- [ ] 喚醒與網路變更同時發生時，只重連一次（看 log 裡的連線嘗試次數）
- [ ] 連線、斷線各 10 次，過程中不會因為 utun 介面變動而多觸發任何重建
- [ ] 自動重連的 `up` 執行中按「斷線」→ 最後狀態是未連線，且不再自動重連
- [ ] 輔助程式還是舊版時，App 仍可連線、斷線，環境檢查提示更新

### 3.7 風險

- 喚醒後網路還沒就緒就重連，會白白失敗一次。靠延遲時間與退避處理，實測後再調整秒數。
- 縮短重送參數後，網路品質差的環境（例：訊號不穩的熱點）可能被誤判成失聯，造成比較頻繁的重建。實測後再決定數值（Q6）。

## 4. F2 非預期斷線通知

### 4.1 行為規格

- 用 `UNUserNotificationCenter` 發 macOS 通知，第一次需要時才請求通知權限。
- **「掉線」的定義**：`wantConnected == true` 時沒有連線的狀態**持續超過 30 秒**，從「通道失聯」或「App 開始重建通道」起算。所以喚醒、換網路後的重建如果 30 秒內成功，不算掉線；超過 30 秒還沒連上，就算掉線，一樣發通知。
- 通知時機：
  - 掉線（依上面的定義）
  - 掉線後恢復連線（只有先前發過掉線通知時才發）
- 同一次掉線只通知一次，恢復前不重複發。
- 設定頁可以關閉通知。
- 待確認：ad-hoc 簽章的 App 能不能正常請求通知權限、顯示通知（Q5）。如果不行，這項要等 F6 完成。

### 4.2 驗收條件

- [ ] 用 §3.6 的 `pfctl` 方式擋住閘道 → 約 60 秒內（偵測約 26 秒＋30 秒寬限）收到一次掉線通知，之後持續擋住也不會重複通知
- [ ] 解除封鎖、自動恢復後 → 收到恢復通知
- [ ] 睡眠喚醒後自動重建通道 → **不會**收到通知
- [ ] 手動斷線 → 不會收到通知
- [ ] 關閉通知選項後，上述情況都不會收到

## 5. F3 App 內建診斷報告

### 5.1 目標

同事遇到問題時，按一個按鈕就產生一份報告檔，直接傳給管理者。**不需要斷線**，也**不能包含密碼、PSK 或金鑰**。

### 5.2 行為規格

- 「環境檢查」頁新增「產生診斷報告」按鈕。完成後在桌面產生 `SplitSwan-診斷-<時間>.txt`，並在 Finder 中選取它。
- 報告內容：

| 段落 | 來源 |
|------|------|
| App 版本、macOS 版本、晶片 | `Bundle`、`ProcessInfo`、`uname -m` |
| 環境檢查結果 | `EnvChecker.items` |
| 連線狀態與 SA | 輔助程式 `status`、`sas` |
| 設定摘要 | 閘道、通道網段、帳號（**密碼與 PSK 只寫「已設定／未設定」**） |
| F4 的閘道連線紀錄 | UserDefaults |
| 通道網段內每個目標走哪個介面 | `route -n get`（跟 `diag.sh` 相同的推導規則） |
| DNS 設定 | `scutil --dns` 前 40 行 |
| 外網探測 | 系統 DNS 解析一個固定網域、HTTPS 連線一次，各限時 5 秒 |
| charon 最近的 log | 直接讀 log 檔最後 300 行（見 5.3） |

- 產生報告時按鈕停用並顯示進度，整份報告要在 20 秒內完成。

### 5.3 需要的改動

- **log 位置**：`install-root.sh` 建立 root 擁有的目錄 `/var/log/splitswan/`（`root:wheel`、755），並**預先建立** `/var/log/splitswan/charon.log`（`root:wheel`、644）。權限不依賴 sudo 的 umask；`logtrim` 每次執行也會重新 `chmod 644`。
  - 目錄是 root 擁有、一般使用者不能寫入，所以不會被放 symlink 導向其他檔案；log 檔權限 644，App 可以直接讀，不需要另外的讀取子命令。
- **log 設定**：App 儲存設定時，產生 `/opt/homebrew/etc/strongswan.d/splitswan.conf`，內容包括 §2.2 的重送參數與 filelog 設定，再呼叫輔助程式 `reload-settings` 套用（Q2）。
  - **log 等級固定為 1**（基本控制訊息），不提供調整。等級越高越詳細，最高等級會包含金鑰等敏感資料。
  - filelog **固定設 `append = yes`、`flush_line = yes`**：`append = no` 時檔案以覆寫方式開啟，就地截斷後會留下空洞；`flush_line` 預設是 no，報告可能讀不到最新幾行。
- **大小控制**：filelog 沒有輪替功能，改由輔助程式 `logtrim` 處理：
  - 每次連線嘗試前、以及 App 執行中每小時，各呼叫一次
  - **就地截斷**：先取最後 1 MB，再寫回原檔（檔案不換新），charon 持有的檔案仍然有效。不可以用「寫新檔再改名」的方式，否則 charon 之後會寫進已經被取代的舊檔。因為 `append = yes`，charon 每次寫入都接在當下的檔尾，截斷後不會產生空洞
  - 截斷的瞬間 charon 剛好寫入的幾行可能遺失。這是診斷用的 log，可以接受
- **遮蔽**：寫入報告前，用正則把 `secret = "..."`、`PSK`、`password` 相關字串整段換成 `***`。要有一個測試：用含已知假密碼的輸入跑遮蔽，確認輸出裡找不到那個字串。
- `diag.sh` 保留給開發者用（它會主動連線再斷線）；App 內的報告只做「現況快照」。

### 5.4 驗收條件

- [ ] 已連線、未連線兩種狀態下都能產生報告，而且不會改變連線狀態
- [ ] 報告裡找不到密碼與 PSK：用真實設定產生一份，再 grep 實際的密碼與 PSK 字串，必須 0 命中
- [ ] 報告包含最近一次協商的 charon log：刻意打錯一次密碼再連線，報告裡要看得到認證失敗的紀錄
- [ ] 截斷有效：先把 log 檔灌到 2.5 MB（以 root 附加假資料），再觸發一次連線 → log 檔變成約 1 MB，之後 charon 仍持續寫入同一個檔案（inode 不變、最後幾行是這次連線的紀錄）、檔案中沒有空洞（檔案大小與實際內容一致）
- [ ] 20 秒內完成

### 5.5 已知限制

`/opt/homebrew/etc/strongswan.d/` 是一般使用者可寫入的目錄，裡面的設定由以 root 執行的 charon 讀取。有心人可以改 filelog 的路徑，讓 charon 以 root 身分寫入任意檔案。這跟 README「安全」一節寫的 Homebrew 執行檔可被替換屬於同一類限制，本版不處理。

## 6. F4 依連線紀錄選閘道

### 6.1 目標

「自動輪替」不再固定從 VPN1 開始，改成先試最可能成功、最快的那台。

### 6.2 行為規格

- 背景：連線前無法可靠地量出每台閘道的延遲（§1），所以改用**過去的實際連線結果**排序。
- 自動輪替改由 App 逐台呼叫 `up N`（§2.1），每次嘗試都記錄 `(閘道, 成功與否, 耗時, 時間)`。每台保留最近 10 筆，存在 UserDefaults。
- 排序規則（**由上而下，前面的規則優先**）：
  1. 冷卻中的閘道（10 分鐘內失敗過）排到最後，但仍然會嘗試，不會完全跳過
  2. 上次成功連上的閘道排第一
  3. 其餘依「最近 10 次的成功率」由高到低，同分時比平均耗時
  4. 沒有紀錄的閘道排在有紀錄的後面，照設定順序
- 所以「上次成功、但剛剛失敗過」的閘道，會因為規則 1 排到最後。
- 選單與連線頁顯示每台閘道的最近狀態，例：「VPN2 · 上次 3.2 秒連上」、「VPN1 · 最近 3 次失敗」。

### 6.3 驗收條件

- [ ] 上次連上 VPN3 → 下次按「自動輪替」，先試 VPN3
- [ ] VPN3 剛失敗過（冷卻中）→ 下次自動輪替時排在最後
- [ ] 某台連續失敗後，自動輪替會把它排到最後
- [ ] 清除紀錄後，恢復設定的順序
- [ ] 直接按 VPN1／2／3 指定連線時，不受排序影響，但結果一樣會記錄

## 7. F5 通道網段集中管理

### 7.1 目標

新增全公司共用的主機時，不必重發設定檔、也不必每個人重新匯入。

### 7.2 方案比較

| 方案 | 做法 | 優點 | 缺點 |
|------|------|------|------|
| **A. 閘道推送（建議）** | 請 IT 在 FortiGate 的 IKEv2 dial-up 設定 split tunnel 網段；客戶端送出 `0.0.0.0/0`，由閘道縮小（narrow）成公司網段 | 網段只需要在閘道維護一份；[推論] 如果 IT 對 FortiClient 也套用同一份設定，FortiClient 使用者的視訊會議也不會再繞去公司 | 需要 IT 配合；**FortiGate 在 IKEv2 下是用縮小 traffic selector 的方式，還是用 Mode Config 屬性推送網段，要實測** |
| B. 遠端設定檔 | App 定期從一個網址下載 `company.env`（例：VPN 連上後，從內網主機下載） | 不需要動閘道 | 要架主機並維護；要處理下載失敗與驗證 |
| C. 維持現況 | 管理者重發 `company.env`，使用者重新匯入 | 不用開發 | 每次都要人工處理 |

### 7.3 方案 A 的客戶端改動（IT 設定好之後）

- 設定頁新增選項「使用閘道提供的網段」。勾選後 `remote_ts = 0.0.0.0/0`，由閘道縮小。
- 連線後從 `sas` 讀出實際的 remote TS，顯示在連線頁。
- **安全閥**：如果閘道**沒有**縮小（實際的 remote TS 還是 `0.0.0.0/0`），就變成全流量模式，會碰到已知的 DNS 問題。這時要立刻斷線，並提示「閘道未提供網段，請改回手動網段」。
- 如果閘道直接拒絕 `0.0.0.0/0`（連線失敗、log 出現 `TS_UNACCEPTABLE`），同樣提示改回手動網段。

### 7.4 驗收條件

- 可以先做先驗，不必等 IT（兩種結果擇一出現，都要有正確提示）：
  - [ ] 勾選「使用閘道提供的網段」並連線到**目前還沒設定 split tunnel 的閘道**：若連上且 remote TS 為 `0.0.0.0/0` → 5 秒內自動斷線並提示；若閘道拒絕 → 連線失敗並提示改回手動網段
- 以下要等 IT 設定好才能驗：
  - [ ] 連線後 `sas` 顯示的 remote TS 與閘道設定一致
  - [ ] 外網與 DNS 正常（系統 DNS 能解析外部網域、HTTPS 可以連線）

## 8. F6 Apple 簽章公證

- 需要 Apple Developer Program 帳號（年費制），用 Developer ID Application 憑證簽章。
- `build.sh` 改動：
  - `codesign --options runtime --timestamp`（開啟 hardened runtime）
  - 加 entitlement `com.apple.security.automation.apple-events`：App 用 `NSAppleScript` 控制終端機（「開啟連線 log」），在 hardened runtime 下需要它。`Info.plist` 已經有 `NSAppleEventsUsageDescription`（`build.sh` 產生），不用另外加。
  - 「安裝系統元件」是另外啟動 `osascript` 程序執行，不是 App 本身送 Apple Event，**不需要**這個 entitlement，但要實測確認 hardened runtime 下仍然正常。
- `make-dmg.sh` 改動：執行 `xcrun notarytool submit … --wait` 之後，再執行 `xcrun stapler staple`。
- 憑證與 notarytool 的認證資訊**不進 repo**，改用 keychain profile。

### 驗收條件

- [ ] 從別台 Mac 下載 dmg 後直接點開，不會出現「無法驗證開發者」
- [ ] `spctl -a -vv /Applications/SplitSwan.app` 顯示 `source=Notarized Developer ID`
- [ ] 「開啟連線 log」與「安裝系統元件」兩個功能，在 hardened runtime 下仍然正常

## 9. 不在本版範圍

- 全流量模式（`0.0.0.0/0`）的 DNS 問題：F5 方案 A 的安全閥會擋掉這個情境，暫不處理根因。
- Intel Mac 支援（Homebrew 路徑在 `/usr/local`）：要把路徑改成執行時偵測，工作量不大，但目前沒有需求。
- 多組公司設定（同時連不同公司的 VPN）。
- §5.5 的 root 讀取使用者可寫入設定的限制。
